## Epoch and publication ordering

A read resets its per-attempt invalidation flag through the coordinator, then captures a token under the shared `RLock` before initial validation. At each fake authorization/release/decrypt/audit/publication phase and each candidate chunk, it checks the token before and after callback-capable validation. Changed epochs deny; they are never silently refreshed. Iterator advancement and user hooks remain outside the locked final interval. Fixed `FakeKey.step` uses internal built-in event storage and owned fault values; it is not a real key operation. The expected internal read-audit append uses the exact `AuditLog` and an internally built record. Only after the preceding epoch check, it must advance the epoch by exactly one; the token is then advanced by one. External audit mutations remain invalidating. Denial/partial-exposure audit happens only after the protected attempt has failed.

For the deterministic standard fixture, a successful read enters at epoch 10, coordinated invalidation reset advances it to 11 and establishes token 11, the owned audit advances it to 12 and the token becomes 12, and the final publication checks 12 before append. In the tested invalidated schedule, entry is 10, token is 11, owned audit makes token/state 12, then a no-op issuer mutation during final inventory validation advances state to 13. The post-validation epoch check denies before append; denial audit then makes the observed exit epoch 14. Numbers are fixture-specific, not a persistent version contract.

After all candidate validation, the broker checks withdrawal and invalidation, obtains the exact coordinator and fixed sink, verifies the sink is a built-in list, then compares the coordinator's private built-in integer epoch with the built-in token. The only operation after the final successful comparison is `list.append(sink, chunk)` while the same lock is held. No input hash, equality, iterator, user hook, or custom sink operation occurs in that interval. This reasoning assumes cooperative private-field boundaries, exact internal classes and no monkeypatching; it does not establish hardware, process, storage or cryptographic security.
