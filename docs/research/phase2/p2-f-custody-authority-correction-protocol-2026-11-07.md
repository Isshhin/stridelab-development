## 1. Initial target and trust boundary

Select as the **initial qualification candidate** the current user-controlled Windows workstation, in an isolated, invented-data-only local test workspace, using a supported 64-bit Windows build and a local non-roaming service profile. This identifies a class and intended host, not a verified or approved machine: before execution the controller must privately freeze the machine identity, exact OS build, filesystem/volume, TPM identity and firmware, executable hashes, local principals and roles; if unavailable the target is NOT SELECTED and tests cannot start. User-reported TBS communication is not proof this host meets the controls. No production or pilot TPM index or key is used.

Define **QROOT** as a freshly created dedicated local test directory outside Git, sync, profiles containing personal records, network shares and actual data; the exact absolute path is privately fixed and verified to be a new empty descendant of the approved test volume before any action. `QROOT/data` contains encrypted invented object versions and work files; `QROOT/cache` contains rebuildable projections; `QROOT/evidence` contains reviewed non-identifying test evidence; `QROOT/restore` is closed scratch; `QROOT/backup` contains only explicitly generated invented encrypted snapshots. These directories are roles, not deployed paths. They cannot supply trusted currentness.

The authority trust domain is the enrolled TPM and its dedicated qualification NV objects, plus the broker identity and independently protected commitment inventory described below; it is **outside QROOT backup and restore** even though on the same workstation. The candidate uses a dedicated local Windows service account with loaded user profile, no interactive login and exclusive permission to access the ledger/inventory/key store and TPM authorization; a local ACL-restricted named pipe admits authenticated operator commands. Steward can submit authenticated restrictive requests, custodian handles controlled backup and deletion; neither can issue active authority outside the broker. Ordinary operator, test viewer, restores and data importers may not write authority/inventory, unwrap keys, invoke TPM issuance, select a backup as current, or start a second broker. Externally supplied files, clocks, snapshots and client requests are untrusted. Admin, kernel compromise, TPM clear/replacement and memory inspection are outside the ordinary-user isolation claim; such changes cause shutdown/re-enrollment and require risk review. Named roles and ACLs are planned, not verified.

## 2. Authority, inventory and sole issuance

One authority identity is `(qualification_namespace, account_scope, purpose, partition, authority_id)`, each component an opaque locally generated identifier; object records add object id, immutable version and lineage digest. A broker operation has a unique operation id and exact intent hash. Each committed authority transaction advances a global non-reusable generation `N`, covering the complete canonical authority state **and** the independently current object/tombstone inventory root for that generation. Each head commits schema/version, previous commitment, N, operation id, authority scope/state, grant restrictions, inventory root, anchor identity and time policy. Authentication and hashes protect binding only under the listed key/issuer assumptions; they do not alone provide freshness.

**Candidate witness mechanism, explicitly unverified:** one enrolled TPM monotonic NV counter `C` is the fresh generation anchor, and a separate protected per-generation write-once commitment slot `W[N]` holds the canonical committed-head/inventory digest and operation id. Slots must be creatable exactly once for a given generation, readable and verifiably write-locked, non-replaceable/non-deletable by the broker or ordinary operator until the namespace is retired, and inaccessible to stale/restored issuers. The single broker owns issuance credentials; OS service singleton plus an exclusive named cross-process transition gate serializes transitions, with denied second service instance and no alternate key/TPM writer. Unique slot addressing is deterministically mapped to `(enrolled namespace, N)` and a collision or exhaustion is CLOSED. The exact TPM policy, index mapping, capacity, command availability, write/lock atomicity, owner/reset/admin exposure, nonrollback and persistence are **requirements to verify**, not asserted TPM features. If any property cannot be established, the proposal cannot claim sole issuance or anti-rollback: remain CLOSED and independently design a separately controlled linearizable, nonrollback compare-and-set witness; do not silently substitute a file, MAC, database lock or same-backup journal.

For normal commit, while the exclusive gate is held: (1) validate current enrolled anchor, `C=N`, immutable `W[N]`, authenticated head and inventory root, and no unresolved restrictive request; (2) durably record an authenticated intent containing operation id, expected N, exact candidate digest and restriction/transition; (3) increment `C` exactly once and freshly read `N+1`; (4) create and write-lock exactly `W[N+1]` with the candidate commitment, read it back and validate its binding; (5) durably install/flush authenticated head and independently maintained inventory matching the commitment; (6) audit and acknowledge only after all checks and required fence. No read is allowed during incomplete transitions. The authority state is current only when counter, unique locked slot, authenticated ledger, inventory root, enrollment and authorization all agree; a single chosen file never determines authority.

If two issuers contend, only the gate holder may transition; a losing/unverified contender denies without issuing. A TPM conflict, occupied slot, inconsistent hash, gate loss, unverifiable lock or unexpected counter closes all scope; never retry issuance by selecting an arbitrary winner. The uniqueness guarantee is **conditional on** independently qualified TPM slot immutability and writer exclusivity in the stated threat model. A prototype using files or process-local locks is not evidence of these conditions. Counter increment and slot write are not a single atomic transaction; partial state is handled by closed recovery, not presumed atomicity.

Inventory is a separately authenticated canonical full mapping in a distinct authority directory and restore domain, committed by `W[N]` alongside the head. Rows hold authority/object IDs, N, issued/current/superseded/withdrawn/deleted/invalidated/pending status, object version, lineage and references to authorized key disposition. Only the broker updates it under the same gate; copies returned to clients are non-authoritative. A payload's absence is **never** permission to issue. A new grant requires explicit enrollment and a new authorized operation; any missing authority, row, lineage, alias or root is DENY/QUARANTINE. Unknown aliases stay denied, never matched by proximity.

Retain restrictive tombstones for the approved lifecycle, keyed by minimum protected scoped tokens with separate lawful-basis and expiry decisions. If a retention deadline requires deletion of the token or mapping, the old namespace is permanently closed to reuse and unresolved future identities are denied; do not assert a permanent identifying tombstone is lawful or recreate a mapping. Superseded/withdrawn/deleted status in the current verified inventory wins over stale payloads and old backups. This is a design requirement; it does not establish real legal authority or effective deletion.

## 3. Rollback and withdrawal

Freshly read `C` and `W[C]` before ordinary key release. A restored old inventory, head or payload must match the exact current committed generation, inventory root, identity, scope, version and active status; stale, partial, mixed, malformed, missing or newer-than-metadata data is not authoritative. Metadata newer than payload is unavailable, not a reason to recreate it. If witness/counter/slot is absent, reset, mismatched, unreachable, unverified or itself possibly rolled back, no cryptographic anti-rollback claim applies: **CLOSED**, no decrypt, and escalate for independent recovery. The proposed counter plus write-once slots only provides anti-rollback if all target assumptions are demonstrated; a TPM counter by itself does not prove non-equivocation.

On verified withdrawal receipt, the broker atomically closes admission/publication for the scope under the process-wide gate/receipt fence; its receipt linearization event precedes any later output. Already delivered output is recorded as escaped, not recalled. Persist restrictive intent; stop/finish and fence in-flight unwrap/decrypt/output; then execute the generation/slot/head/inventory protocol for a withdrawn tombstone and descendant invalidations. The **durable authority-loss point** is successful verification of `C=N+1` and locked `W[N+1]` binding the restrictive head and inventory root, with the matching head and inventory durably installed. Until that point receipt is pending, publication remains closed and no completed suppression is acknowledged. Afterward the prior active head is not current. Audit and acknowledge suppression only after the fence; independently enumerate/remove or quarantine encrypted payloads, wrappers, temp, backups and descendants according to approved retention. Key destruction or deletion is complete only after inventoried copies and independent verification; report pending backups and unverified copies separately.

## 4. Interruption and recovery matrix

All starts, reinstalls and restores begin **CLOSED**; reconcile the authenticated withdrawal channel before opening. `UNKNOWN/INCOMPLETE` is never authoritative. A process crash, forced termination, power loss, disappearing lock owner or partial write are equivalent in that no former lock proves completion. The durable record and actual witness must be re-read; temporary files and transaction journals are untrusted evidence, never automatic current heads.

| Interrupt | Mandatory recovery |
|---|---|
| Issuance or replacement before intent/counter | Remain CLOSED; independently reconcile requests, authenticate intent if present; discard/isolate orphan temp, do not infer an active grant. |
| After durable intent; counter outcome unknown | Read actual enrolled counter and slot; never blindly repeat advance. If still old and no conflicting request, an explicitly authorized recovery may abandon the incomplete candidate; otherwise closed. |
| Counter advanced, slot missing/unlocked or malformed | CLOSED. Never create a new active issuance to repair a gap. A verified precommitted restrictive intent may be completed only if the independently reviewed protocol proves exact one-time slot binding; otherwise halt. |
| Slot locked but head/inventory not durably installed | CLOSED. Recover only the exact digest-bound authenticated restrictive state from verified intent; a missing/ambiguous state, or incomplete active grant, remains closed and requires independent adjudication. |
| Withdrawal/deletion after receipt but before restrictive commit | CLOSED; request channel reconciliation required; no completed acknowledgement. Resume only verified restrictive transition; never restore old active access. |
| Inventory/head disagreement or partial metadata/key update | CLOSED; do not choose newer-looking file or reconstruct state from a payload/key. Verify exact locked commitment, object status and key inventory; isolate inconsistent material. |
| Evidence/audit emission failure or lost acknowledgement | CLOSED or restricted as applicable; no completed acknowledgement. Reconcile same operation id and audit; do not re-advance or emit a conflicting head. |
| Partial restore, reinstall or interrupted deletion | CLOSED scratch with processing, sync, viewer and export disabled. Inspect current authority/inventory independently first; resume verified disposal; unknown copies remain UNVERIFIED and block progress. |

## 5. Encryption, key custody and time decision

Candidate data protection: Windows CNG AES-256-GCM authenticated encryption for each immutable invented object/version; its associated data binds namespace, scoped authority, object/version, generation and lineage. Generate a fresh per-version data-encryption key using the platform CSPRNG; each key is used for **one** encryption invocation with a 96-bit nonce, so retries create a new key/object version and never repeat encryption under the same key/nonce. Collision and randomness assumptions require implementation review; no real key is generated here. Encrypt original copies, working/temp, normalized/derived values and permitted backups; protect or exclude swap, logs, cache and crash artifacts. Opaque identifiers, schema and version are not assumed secret but are restricted metadata and must be minimized. AAD is authenticated, not encrypted.

Wrap per-object data keys with **user-scope DPAPI** under the broker's dedicated loaded non-roaming service profile; machine-scope DPAPI is not accepted for this boundary. Only the broker may unwrap, and only after fresh authority plus inventory validation and receipt fence. Wrapped keys live in a separately ACL-restricted key directory; approved encrypted backup copies and key-copy inventory are accounted for, and recovery material is separately held by a named custodian outside ordinary backups. Reinstall with the same eligible profile does not itself restore authority; a changed/deleted account, reset profile, unavailable wrapper or lost TPM identity remains CLOSED pending reviewed recovery. Key recovery never widens authority. Microsoft documents that `CRYPTPROTECT_LOCAL_MACHINE` permits any user on the machine to decrypt and user scope normally binds the matching user and machine, with exceptions ([CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)). Service-profile behavior, ACLs, recovery, CNG nonce discipline and alternate copies remain unverified.

**Trusted-time decision: B, trusted time is required for real grant and retention deadlines.** Authority *ordering/currentness* uses counter and committed state, not wall time; this cannot determine whether a legal grant or retention deadline has elapsed. Select the existing candidate of a separately administered NTS time-only gateway, e.g. a pinned approved NTS service, issuing an authenticated broker-challenge-bound local attestation with time interval and measured uncertainty. The controller must explicitly approve this processor/link or approve a separately reviewed design that meets the same deadline invariants; without that decision the offline workstation stays disconnected and time-bound access remains CLOSED. The gateway stores no participant files or identifiers; disclose network/service metadata. The time interface must define source and certificate bootstrap, authenticated key/identity, freshness, bounded transport delay and drift, monotonic elapsed-time tracking and conservative expiry using the latest plausible time. Restart, clock reset/rollback, sleep, expired attestation, ambiguous source, excessive uncertainty, offline gateway or missing trusted bootstrap denies time-bound operations. NTS authenticates exchanges; it does not prove server accuracy or eliminate delay attacks ([RFC 8915](https://www.rfc-editor.org/rfc/rfc8915.html)). Source selection, bootstrap and offline-policy acceptance remain unqualified, not silently decided by the use of NTS.

## 6. Restore/reinstall table

| Situation | Required outcome |
|---|---|
| Valid current backup | Closed scratch; compare live independent counter/locked witness/head/inventory and key scope before any unwrap. Open only after channel reconciliation and explicit authorization. |
| Stale or partial/mixed backup; withdrawn or deleted payload | Closed/quarantine; current restrictive inventory wins, never elevate old head or materialized descendants; account for copies and cleanup. |
| Payload without inventory; inventory without payload | DENY/QUARANTINE; absence is not permission to recreate. Missing payload is unavailable, never reissued merely to make restore pass. |
| Key without metadata; metadata without key | No unwrap/read; isolate orphan material or report unavailable key, respectively. Recovery cannot confer authorization. |
| Reinstall with data | Newly installed broker begins closed, revalidates enrolled witness, service identity and independent inventory and reconciles pending requests; no automatic grant. |
| Reinstall without data | No ordinary processing; loss/recovery is separately reviewed, never construct authority from copied keys or a convenient generation. |
| Changed OS/user account, TPM loss/reset or uncertain identity | Closed; new controlled enrollment/migration and independent review, or abandon; never reset protected hardware as a workaround. |

## 7. Later non-destructive capability preflight (not executed)

This is a **protocol to review**, not a command authorization. Before any execution freeze the private target identifiers, exact OS/build/tool versions, observer, workspace resolved absolute path, explicit operation list and non-identifying evidence scheme. A read-only first stage may inspect documented OS/service/filesystem/TPM capabilities and TBS command access without changing TPM policy or NV. Microsoft's [TBS command-blocking documentation](https://learn.microsoft.com/en-us/windows/win32/tbs/command-blocking) confirms command eligibility is policy/platform-dependent; enumeration alone cannot establish successful authorization. Stop on unexpected user data, target ambiguity, unavailable permissions, unfamiliar TPM state, or any destructive/persistent operation not expressly approved.

In a **separately approved disposable invented-data sandbox**, create only a verified empty descendant of QROOT; test exclusive creation and competing-process lock with deterministic barriers; atomic replacement/readback and interrupted write with synthetic files; user-profile protection/unprotection with disposable synthetic bytes; and private copy/restore in isolated scratch. A normal reboot or forced process termination requires separate authorization and its impact on the user's environment must be reviewed. Do not touch production NV, change policy, clear TPM, create real pilot keys, access existing data or assume a preflight proves counter/slot policy. PASS for an individual check requires both expected success and intended negative denial, captured version/config, exact operation, observer, reproducible output and cleanup; FAIL/UNSUPPORTED/NOT RUN when not established. Tear down only the verified sandbox descendants with native Windows operations after path verification; retain sanitized non-identifying evidence in the approved evidence area. Failure, unexpected access, partial cleanup, unknown behavior or insufficient isolation stops progression. Integrated synthetic crash/restore qualification requires a separate approved plan and is not run here.
