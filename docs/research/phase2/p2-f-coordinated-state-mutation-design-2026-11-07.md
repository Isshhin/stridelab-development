Direct mutation appears throughout the focused and review tests to model rollback, corruption, lost responses and interrupted recovery. The contract requires those *behaviors and outcomes*, not a public API promising that arbitrary Python attributes or nested dictionaries can be edited. Preserve fault scenarios via explicit model controls. Python privacy is a cooperative harness boundary, not protection against code deliberately reaching private internals, monkeypatching objects or mutating process memory.

## Options

**A — shared lock:** One lock for mutations and validation is simpler than today's split ownership and serializes other threads. It is insufficient alone: an `RLock` permits same-thread callback reentry; a non-reentrant lock can deadlock on such a callback. A callback may change a previously checked invariant inside the critical section. Existing direct writes bypass either lock. Migration is material because tests inject faults directly.

**B — epoch alone:** Capture and compare a monotonic mutation epoch to detect an intervening change, including a change that is later reverted. Without controlled mutation paths and a lock around the epoch check and append, direct writes can omit the increment and another thread can race the final comparison. An exception after a partial mutation must not omit the increment.

**C — immutable whole-state snapshot:** A single immutable aggregate and atomic replacement can represent a coherent state and make old snapshots stable, but it requires replacing much of the anchor/issuer/ledger/inventory recovery model and migrating many tests. It still needs a synchronized current-snapshot check at append, and must not retain mutable user objects. Too broad for this synthetic correction.

**D — broker-owned mutation API:** Controlled paths and read-only/copy-out views remove supported untracked writes, including nested dictionaries. Explicit synthetic fault APIs preserve rollback and corruption tests. Ownership alone does not order a different thread's mutation against publication or detect same-thread reentry; it needs synchronization and a mutation signal. Fault operations must model independently changing authority and inventory, not pretend every real system is broker-owned.

**E — minimum hybrid, selected:** One synthetic coordinator owns the publication-relevant model state and its shared `RLock`; all supported mutations go through it, and a monotonic in-process epoch identifies any attempted relevant change. Keep existing domain objects as facades only if they cannot leak writable state. This is A + B + D, with small immutable/copy-out values as an implementation detail, not a full immutable-state redesign. The coordinator is a simulation of ordering, not a real authority service.

## Selected protocol and ownership rules

1. Give one coordinator to all anchor, issuer, ledger, inventory and broker objects in one model instance. Constructors/attach must reject mixed coordinators or deliberately join them only while closed; independently modeled authority/inventory can still be changed through distinct coordinator-controlled APIs. Private backing storage includes nested maps and cannot be returned by reference; expose immutable values or defensive copies made at a safe boundary. No public setter or escaped mutable alias is a supported mutation path.
2. Every supported change to tabled validity, recovery or admission state, including fault toggles, identity/issuer/anchor replacement, direct modeled corruption, withdrawal, close/enroll/reconcile and data-version updates, takes the same lock and advances the coordinator's private monotonically increasing exact built-in integer epoch **before the first possible state change**, even if the mutation later raises, is reverted or is a no-op attempt that is treated as invalidating. Audit/output bookkeeping that cannot influence later admission may be excluded only after an explicit call-site inventory. Do not reset/reuse an epoch on restore, restart, or reattachment in a live coordinator; a fresh coordinator starts closed and cannot validate an old read token.
3. A read captures a starting epoch under the lock before obtaining/validating its state. Each authorization/release/publication boundary obtains the lock, checks that the operation remains valid and the epoch still equals the read token, validates authority, issuer, inventory, data, scope, time and stop state, then compares the same epoch again **after every callback-capable validation and before the effect**. An epoch change, including a change during validation that was caught by caller code, denies rather than retries. The final comparison and built-in-list append are adjacent under the lock, using private exact built-in epoch/boolean storage and a fixed internal output sink: no user comparison, hash, hook, custom descriptor, custom list/append, or other callback in that interval. Candidate iterator advancement and user hooks stay outside this final interval. Where release/decrypt/audit steps themselves can call out, they must have an equivalent fenced effect boundary or be made internal non-callback operations; do not claim the final append fence protects an earlier effect.
4. Cross-thread mutations wait only for the bounded critical section, then advance the epoch under the same lock; the lock acquisition determines whether publication or the mutation wins. A withdrawal is considered *received by the model* when its state is set under this lock, not when a caller merely starts waiting; once received, no later chunk appends. Acknowledgement still waits for in-flight work to finish. Do not wait for another thread or call arbitrary hooks while holding the lock. Same-thread reentrant mutation can run under `RLock`, but its epoch bump invalidates the outer operation; rejected nested operations must still set the operation-invalid state through an owner-aware coordinated path, even if the inner exception is caught. A competing reader is denied without invalidating the current owner. Preserve the explicit withdrawal/invalid checks and partial-output accounting.
5. The read token persists across chunks and phase callbacks. A mutation between chunks denies the remaining output even if the new state happens to validate; already appended chunks remain accurately recorded as escaped. After denial, `finally` clears owner/busy and releases gate and lock; later behavior depends on the resulting closed, withdrawal and reconciliation state. Transition intent, uncertain advance, commit, inventory suppression and recovery remain separately injectable boundaries, rather than being collapsed into an unrealistically atomic real-world transaction.

The argument is conditional on complete mediation: another thread cannot mutate between final comparison and append while the lock is held; a same-thread callback that changes any mediated invariant changes the token before the check; there is no callback-capable operation after that check. A raw private-field mutation, arbitrary monkeypatch, shared mutable input alias, custom output sink, external service, process crash or real hardware is outside that proof. The implementation must establish the conditions, not merely add an epoch field. Prevalidate/canonicalize inputs to exact immutable built-ins without silently changing the supported benign-subclass behavior; if a subclass is accepted, any conversion callbacks occur before token capture or inside a checked epoch window, and no mutable caller reference enters internal state.

## Test migration and acceptance

Introduce explicit fixture-only coordinator methods for deterministic anchor advancement/failure, forged head/intent/issuer condition, inventory rollback/suppression and modeled-data version changes. Use named validation/effect schedule hooks or controlled callback objects at defined points rather than relying only on the seventh hash invocation. Preserve tests for actual hash/equality callback reentry as well as benign subclasses; inject through the supported coordinated API, assert a mutation really occurred or was deliberately rejected, catch the inner denial where relevant, and assert the outer operation cannot emit stale output. Keep historical review artifacts; migrate executable review schedules without deleting their semantic assertions.

Acceptance for later implementation:

- Both recorded anchor-during-inventory and inventory-during-data schedules are normal passing regressions, with no stale append; exercise changes restored to their original value and partial mutation followed by an exception.
- Every owned field, nested map and fault path has mutation coverage, including issuer commitment/availability, `closed`, enrollment, restore/reconcile, removal/replacement and direct alias attempts. A copied-out view cannot change internal state; unsupported direct writes fail or do not affect it. Verify no epoch reset/reuse or mixed-coordinator bypass.
- Preserve withdrawal hash/equality, data lookup between chunks, both flags, nested and unrelated-thread cases, iterator failures, stale state, idempotence, conflicts, restart/recovery, interruption, partial accounting, accepted benign subclass, time-bound decisions and closed-state behavior. Assert owner/gate cleanup and subsequent permitted or denied behavior.
- Deterministic thread barriers establish both publication-before-receipt and receipt-before-publication ordering and avoid deadlocks, including same-thread reentry. Include mutation between chunks, during each validation and during callback-capable fake effects. Verify no callbacks in the comparison-to-append interval.
- Run focused authority tests; all five review groups, including migrated reproductions; durable, P2 and full research suites. Report platform skips and separately request independent review of the exact implementation head. Do not infer real custody guarantees.

## Later task boundary and complexity

Expected complexity is moderate: the algorithm is small, but complete mutation ownership, non-leaking nested views, lock ordering, recovery paths and test migration touch many call sites. Likely risks are accidental compatibility breaks in fixtures, missed epoch updates, deadlocks/reentrancy, modeling away independent state, and silently weakening the withdrawal receipt boundary. The design is not an implementation or test result.
