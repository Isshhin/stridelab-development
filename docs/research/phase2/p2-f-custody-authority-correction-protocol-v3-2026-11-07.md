## Anchor: required invariant and candidates

One namespace needs one current durable nonrollback committed generation binding exact authority and restrictive inventory state, prior reference, immutable operation ID, request digest and disposition. Conflicting writes serialize; stale writers cannot overwrite newer state; reset/replacement and divergent histories must be detected; interrupted commits cannot create active state from incomplete evidence. A local file, DB, mutex, MAC or journal alone cannot provide this.

Remote candidate trust root: independently protected service identity, administrative controls and independent continuity witness, all hypothetical. Writers need individually revocable credentials and server-enforced scope and generation checks; a shared service token does not identify one executable. Competing writes require atomic compare-and-set, one winner; stale credentials require server-side revocation checked in the same trusted ordering. Authorized administrators could delete, restore or replace service state absent independent continuity; administrators and service compromise can violate integrity if the trust root is compromised. Retry must query the authoritative operation registry linearly, not local cache. Connectivity loss closes; offline active operation is unsupported. Backup is never current authority; restore/reinstall starts closed and needs independent epoch/continuity and exact state proof. A separate external processor would receive at least pseudonymous namespace IDs, digests and timing, with linkability and legal/operational consequences; opaque hashes do not guarantee anonymity. Cluster operations, identity, backup and 24-hour availability impose complexity. Windows compatibility and exact deployment remain untested.

## Withdrawal and publication

Invariant requested: once SOURCE_WITHDRAWAL_ACCEPTED is durably linearized, no later authority-sensitive output may be externally committed. A signed checkpoint only authenticates what it says, not absent withdrawals or freshness.

Model A: freshness leases cannot ensure the invariant merely by expiry; a withdrawal accepted during an outstanding lease races with output. A source could defer *acceptance* until all leases expire and every output channel is fenced/drained, but a stalled broker or unbounded in-flight output makes acceptance unbounded; time and revocation correctness also require a trusted interval. Issuance, coverage, replay and source equivocation are not resolved by a signature. A source that accepts immediately must revoke and prove all outputs stopped before acceptance; a partition prevents such proof. No model selected.

Model B: synchronous source participation is promising only if the authoritative source and actual externally visible output commit share one enforceable serialization boundary. A pre-publication authorization or reservation alone is insufficient: the broker can pause after authorization while withdrawal commits, then release bytes. An external recipient, export filesystem, backup, or downstream channel outside the boundary defeats the claimed ordering. One possible restricted future model is a trusted gateway that is the *only* output endpoint, serializes each actual irrevocable release with source withdrawal acceptance, and is able to fence and account for in-flight writes. The exact transport, receiver observation/commit definition, buffer and crash semantics, and independent continuity are not specified. A durable enqueue is not the same as later externally visible release; this ambiguity cannot be relabeled away. Availability requires source and gateway reachable; no local/offline output. Batching requires one atomic batch release or per-item checks, with no delayed release past withdrawal. This is an analysis, not a selected protocol.

Proposed ordering for any future viable model:
- BROKER_COMPLETENESS_PROVEN is a fresh atomic fact at the shared serialization boundary, not a cached checkpoint. OUTPUT_RESERVED is provisional and carries no irrevocable permission.
- OUTPUT_COMMITTED is the actual externally visible irrevocable release, serialized at the same boundary as SOURCE_WITHDRAWAL_ACCEPTED. If output wins, it precedes acceptance; any later release must be rejected. If withdrawal wins, output cannot commit. No ambiguous in-flight release can be treated as resolved merely from an RPC response.
- WITHDRAWAL_DELIVERED_TO_BROKER can occur later; it is not the acceptance point. After delivery the broker fences, cancels queues and reconciles. AUTHORITY_RESTRICTIVE_COMMIT requires independently anchored exact restrictive state and verified output fencing; WITHDRAWAL_ACKNOWLEDGED requires this commit and durable confirmation. Delivery, restrictive commit and acknowledgement can lag acceptance, but none restores output.
- During disconnect, source outage, partition, missing identity, stale lease, delayed or repeated checkpoint, unknown result, restart, reinstall or insufficient proof: CLOSED. Repeated requests with same ID/hash return independently established prior outcome; conflicting ID/hash closes. Broker crash does not release a reserved output. A restore cannot supply currentness. Queued work, derived data, exports and backups are output and require the same boundary. Already escaped data cannot be recalled; pending/in-flight data requires a proven fence before acceptance, or acceptance must wait. Unknown release ordering closes and requires adjudication.

Source equivocation and discontinuity need an independently selected trust root and enforcement. No proof yet covers all output channels, crash and network buffering.

## Local Windows durability and records

A proposed cache procedure uses an exclusively created new file on the same local NTFS volume; write all bytes with checked completion, `FlushFileBuffers` the write-capable file handle, close handles as required, then replace an existing name with `ReplaceFileW`. First creation and failures require separate treatment; no cross-volume copy fallback. Replacement's documented error states must be inspected rather than assumed all-or-nothing. Reopen and validate; neither a successful reopen nor a local record makes it authority. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [ReplaceFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), [caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching).

API_RETURNED_SUCCESS means only documented successful call, not namespace power-loss durability. DATA_DURABLE_ACROSS_PROCESS_CRASH requires recovery verification and depends on OS/storage remaining alive; success alone is not an independent proof of the entire multi-step transaction. DATA_DURABLE_ACROSS_OS_CRASH and DATA_DURABLE_ACROSS_POWER_LOSS are TARGET_EVIDENCE_REQUIRED for exact stack, including parent directory metadata, controller/device caches and honest flush support. Microsoft documents write-through requests and NTFS metadata flushing but notes hardware may not support write-through; `REPLACEFILE_WRITE_THROUGH` is unsupported. No generic supported user-mode parent-directory flush sequence is assumed. Close handles is resource cleanup, not itself a persistence proof. Missing, corrupt, truncated, old, newer, unrecognized or ambiguous local state closes; independent anchor and complete exact state are required for recovery, otherwise manual adjudication or permanent unavailability. No active-state reconstruction from digest or backup.

Proposed record freeze for review, not implementation: fixed binary envelope, format version 1; unsigned big-endian fixed-width integers; length-prefixed byte strings, fixed field order, no maps or duplicate fields; maximum envelope 1 MiB; namespace and operation ID exactly 16 bytes; SHA-256 request, prior reference, resulting state and inventory digests each 32 bytes; anchor reference at most 4096 bytes; disposition enum restricted to explicitly defined committed/rejected/restrictive values; length, domain-separated `StrideLab/P2F/local-record/v1\0` and HMAC-SHA-256 over all preceding fields, with a separately protected authentication key. Reject trailing bytes, unknown versions/enums and out-of-range lengths. SHA-256 detects corruption, HMAC authenticates only against outsiders without the key; neither prevents rollback, a malicious key holder, or supplies authority. The canonical encoding of the *state and request* and their exact fields, key lifecycle and anchor authentication still require closure. Local records never establish currentness.

## Operation identity and recovery

First request must atomically compare current generation and absent namespace-scoped ID at the anchor, storing ID, canonical request hash, exact state/inventory roots, previous reference and disposition in the same transaction. Duplicate same hash returns the anchor's original final disposition; ID with differing hash is rejected and closes investigation. Lost response or crash after commit: linearly query authoritative registry, verify exact roots and reconcile; no response means CLOSED. Crash before commit: independently prove absent and current generation before retry; uncertainty closes. A rolled-back DB or reinstall is a cache miss, never proof of non-commit. Competing IDs serialize against expected generation; losers re-evaluate or close, never silently rebase. Concurrent restrictive and permissive operations need a defined independently enforced ordering and publication fence; restrictive receipt must fence immediately and stale permissive commits cannot reopen it. Absent a selected anchor and finished publication boundary these are requirements, not executable semantics.

## Security and trust

Ordinary interactive users are intended adversaries; access control, pipe first-instance creation, local-only clients and reparse-safe handles need independent verification. Same service-token processes and stolen credentials are outside broker executable-isolation protection: they may issue requests unless the anchor independently authenticates and scopes them. Administrators, SYSTEM, kernel compromise, service binary replacement and impersonation are outside the local integrity boundary; they can bypass local enforcement or read/replace keys, requiring closure and incident handling, not a security claim. Remote clients are denied unless a separately authenticated path is designed. Pipe squatting and reparse races must be detected and fail closed, but are not solved by a pipe DACL alone. Copied executables and restored backup do not confer authority; identity and continuity must be independently established. An OS mutex coordinates cooperative threads only.

No trusted wall time is needed for generation ordering; no external trusted time is required for the time-independent read-only preflight. Deadline-dependent use stays disabled; future time gateway pending. Existing CNG AES-GCM plus user-scope DPAPI proposal is unchanged: EVIDENCE_BLOCKED_PENDING_INTEGRATED_TARGET_QUALIFICATION; no DPAPI invocation is authorized.
