# Independent P2-F custody and authority security review

Reviewed proposal: [correction protocol](p2-f-custody-authority-correction-protocol-2026-11-07.md) at `b038d68f8717cee250492bdef93749c8eb98341c`. Prior review preserved at `522fd1076bbeb110dd70fdfdaf259d9c14dfa510`. This is a new desk review, not a target experiment, independent human certification, implementation, or target qualification. No private data, TPM operations, keys, or workstation configuration were used. Findings distinguish specification, Windows exposure and target evidence. The proposal explicitly calls its TPM mechanism conditional; this review does not treat those conditions as proven.

## Decision and findings

**P2F_CUSTODY_AUTHORITY_DESIGN_NEEDS_CORRECTION.** The review does not authorize a preflight. A strictly read-only inventory of public documentation is possible, but the proposed machine preflight needs a precise non-mutating command list and safety boundaries before separate authorization. A later preflight can investigate capabilities without validating custody or authorizing production enrollment. The issues below concern implementability and soundness; an inability to demonstrate a target property is not itself proof that no TPM can support it.

**R1 — witness creation/deletion and split-brain:** the protocol specifies mutually necessary properties but not an implementable authorization policy or lifecycle proving that the creator can create a slot while neither it nor a stale same-credential issuer can replace/delete it. A counter increment is not an atomic compare-and-set of a commitment; write followed by lock leaves an unlocked interval. The named OS gate depends on all credential holders cooperating. Specify enrollment roles, exact TPM hierarchy, attributes, policy, creation and deletion authorization, writer/credential isolation, state authentication, counter attributes and exceptional lifecycle before relying on this construction. A broker that possesses owner authorization for ordinary owner-created indices may also be able to undefine them; a write lock does not change that. Do not claim this necessarily defeats a separately designed policy-delete/platform-controlled scheme: that scheme is not specified or shown accessible.

**R2 — receipt durability and fencing:** the authenticated withdrawal channel is named but not specified as an independently durable, ordered source with receipt, replay, cursor, reconciliation and unavailability semantics. The gate and publication fence lack concrete atomicity and identity rules. After a verified in-memory receipt and a crash before intent, a restored active head is not sufficient to decide whether withdrawal was received. The proposal says remain closed and reconcile, which is safe only if opening actually requires reliable complete reconciliation. Define the channel and the ordering of receipt, output, durable acknowledgment, retry and restart, including what happens when channel completeness cannot be proved.

**R3 — operation and crash state machine:** define canonical serialization, atomic durable intent/head/inventory writes and filesystem flush contract, unique operation-id registry across restoration, and exact restrictive-only recovery authorization and slot binding. In particular, hash-only witness data cannot reconstruct missing state, and a restored intent registry cannot independently prove an operation ID has never been consumed. Ambiguity must remain closed, even if this permanently loses availability. Specify durable journal and witness dependencies without treating the journal as anti-rollback.

**R4 — preflight scope:** section 7 leaves commands, principals, sandbox permissions, cleanup effects, remote exposure and observers unspecified. Merely calling a command read-only does not establish that the API causes no persistence or that the existing target can safely be queried. Freeze an operation-by-operation plan and target before requesting authorization; do not test NV creation, write, increment, lock or undefine under this authorization.

## Evidence and platform distinctions

* **SPECIFICATION_SUPPORT:** [TCG TPM 2.0 architecture](https://trustedcomputinggroup.org/wp-content/uploads/TPM-2.0-1.83-Part-1-Architecture.pdf) describes NV counter indexes and increment semantics. First increment of a newly defined counter initializes it above previous values for the same Name, rather than necessarily at zero; generation mapping must handle this. Orderly counters have special unclean-start behavior and can jump; a strict `N+1` recovery rule needs explicit counter attributes and proof. Counter values have finite size and implementation-defined resource constraints. A counter does not bind a digest, prevent two credentials from racing, or supply operation-id deduplication. TCG [structures](https://trustedcomputinggroup.org/wp-content/uploads/Trusted-Platform-Module-Library-Family-2.0-Level-00-Revision-1.81-Part-2-Structures_8December2023.pdf) distinguish WRITEDEFINE permanent write locking from WRITE_STCLEAR reset/restart-scoped locking and policy deletion. A permanent write lock is not a prohibition on undefinition. [TCG commands](https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-3-Commands-01.38.pdf) describe policy-delete special undefinition for platform-created indices; ordinary owner-created indices require the defining hierarchy authorization for undefinition. Owner-created indexes can be removed by TPM clear. Platform-created policy-delete may require platform authorization and supported commands: it is not automatically available to the application. Clear/reset/replacement and hierarchy management remain explicit trust/lifecycle boundaries. A per-generation NV index consumes finite NV resources, and the lifetime number, handle mapping, collision resistance, exhaustion behavior and policy retirement need a concrete budget. Do not assume arbitrary per-generation slots or reclamation.
* **WINDOWS_ACCESSIBILITY:** [Microsoft TBS command blocking](https://learn.microsoft.com/en-us/windows/win32/tbs/command-blocking) states TPM 2.0 commands are subject to an allow-list and policy; TPM specification support does not establish caller access, sufficient hierarchy authorization, or ability to configure the required policy. [TBS scheduling](https://learn.microsoft.com/en-us/windows/win32/tbs/command-scheduling) schedules commands, not a multi-command transaction. Read-only capability discovery cannot establish write authorization, persistence, policy-delete, power-loss semantics or anti-equivocation.
* **TARGET_EVIDENCE:** none. OS build, TBS filters, account token, hierarchy ownership, exact TPM/firmware, available index resources, commands, NV policy, locks, clear/reset/replacement detection, reboot and power-loss behavior remain unverified. No claim of unsupported hardware is made solely from this absence.

**TPM_WITNESS_DESIGN_REQUIRES_CORRECTION.** Specify a realizable authority and policy boundary, and prove the counter/slot protocol's safety under noncooperating credential holders and interrupted write/lock before target qualification. An alternative witness must provide one durable, nonrollback, non-equivocating commitment for each current generation, bind exact state and operation identity, prevent stale issuers replacing or deleting committed evidence within the stated threat model, serialize conflicting commits, detect reset/replacement and fail closed on uncertainty; recovery must not manufacture active authority. This is an invariant, not a selected replacement.

## Area assessments

Each entry states invariant; mechanism and independent assessment; scenario; correction/evidence; and whether it blocks the requested preflight. Classifications concern readiness for this specific limited step, not a target PASS.

### 1. Target and trust boundary — DESIGN_CORRECTION_REQUIRED
Invariant: ordinary operators and restored data cannot issue, unwrap or redirect authority; test work remains isolated. Mechanism: local service account/profile, QROOT, ACLs, pipe, independent authority directory, administrator/kernel exclusions. Assessment: a service account is a security principal, not proof that only a particular executable may use its token or credentials; no-interactive-logon alone is insufficient. Define service token/privilege and credential theft/impersonation assumptions, allowed logon types, pipe server identity, remote-client denial, reparse-point-safe path handling and authority directory/backup controls. Microsoft's [pipe security guidance](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) warns default DACLs and generic write can grant unintended rights, including pipe-instance creation. Failure: second process under the same token or a squatted pipe bypasses a merely named singleton. Evidence: exact target, ACL/token and negative access checks in later approved tests. Blocks the proposed unspecified sandbox preflight: yes; a narrowly scoped documentation-only study does not require target access.

### 2. TPM witness — DESIGN_CORRECTION_REQUIRED
Invariant: exactly one immutable current commitment binds generation, state, inventory and operation; stale issuers cannot replace it. Mechanism and assessment: counter plus slot is conditional, with R1 and specification/accessibility/target distinctions above. Failure: after creation and write but before durable lock, another authorized writer changes content; or an authorized owner undefines a permanently locked ordinary slot. A counter and cooperative gate alone do not exclude this. Corrections/evidence: R1; policy analysis and later separately authorized synthetic destructive-state testing on an expressly selected disposable target, never this preflight. Blocks this proposed preflight: yes for its unbounded capability claims; no implication that read-only documentation work is unsafe.

### 3. Broker exclusivity — DESIGN_CORRECTION_REQUIRED
Invariant: one logical issuer, including retries, not merely one well-behaved process. Mechanism: service singleton, named gate, broker credentials. Assessment: service manager/mutex may serialize cooperating processes but do not bind TPM commands to a binary or stop a copied process using an available account token; an abandoned gate indicates interruption, not transaction completion. Microsoft explains [service accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts) determine security context. Failure: two holders share credentials; one skips gate and races the other. Correction: define attacker and same-account process assumptions and enforce or prove issuer restriction independently of cooperation; account for gate namespace, DACL, lifetime and operation retries. Evidence: reviewed policy, role and competing-process tests. Blocks proposed sandbox preflight: yes until principals and exact operations are frozen.

### 4. Generation/currentness — DESIGN_CORRECTION_REQUIRED
Invariant: at most one eligible current state, no replay/double advance, each interruption deterministically deny or recover exact restrictive state. Mechanism: intent → increment → slot write/lock → head/inventory → acknowledge. Assessment: missing slot after increment safely denies but may brick the namespace; locked slot without full matching data cannot reconstruct by digest. Initial counter may be nonzero and orderly counter may jump. Neither counter nor hash alone ensures one operation ID advances once; durable deduplication and conflict rules are missing. Failure: lost acknowledgment followed by restored intent database replays the same ID into another generation. Correction: R1/R3, exact error and duplicate-response semantics; do not equate safe closure with successful recovery. Evidence: separately authorized injected crash/retry and flush/power-failure tests. Blocks unspecified mutating sandbox checks: yes.

### 5. Inventory/tombstones — DESIGN_CORRECTION_REQUIRED
Invariant: old payload or inventory cannot reopen withdrawn/deleted authority. Mechanism: independently stored complete inventory root in current witness, scoped opaque IDs and tombstones. Assessment: sound only conditional on unique, nonrollback witness and authenticated canonical schema; independence of a directory from QROOT does not make it rollback-proof. Define ID generation/collision handling, namespace retirement commitment and what authenticated information remains when retention requires deletion. Failure: restored old root plus replaced witness could appear current if R1 fails; missing row or unknown alias must deny. Correction: R1 and canonical authenticated namespace retirement, alias/lineage rules. Evidence: later stale inventory, deletion, alias, key and backup replay tests. Blocks preflight: R4, not a claim that read-only inventory testing is intrinsically unsafe.

### 6. Withdrawal — DESIGN_CORRECTION_REQUIRED
Invariant: once receipt linearizes, no later output; durable authority loss survives restart. Mechanism: receipt fence, stop in-flight work, restrictive commit, audit/ack. Assessment: receipt is an immediate in-process publication prohibition, not itself durable authority loss. `AUTHORITY_CAN_NO_LONGER_BE_USED` is durably established only after restrictive counter/locked witness and matching head/inventory are durably validated and the publication fence has drained; before then scope stays closed and acknowledgment cannot claim completion. The receipt channel/fence must satisfy R2. Failure: crash after receipt before intent, then restart opens from an old head without complete channel reconciliation; in-flight plaintext or backup worker may publish after receipt unless fenced. Correction: R2 with exact in-flight and backup ordering and acknowledgment semantics. Evidence: deterministic schedules and restart, channel outage and failed audit tests. Blocks preflight: R4, not safe read-only documentation.

### 7. Recovery — DESIGN_CORRECTION_REQUIRED
Invariant: no optimistic active reconstruction; failures deny and legitimate unavailability is explicit. Mechanism: startup closed, authenticate and reconcile, restrictive-only recovery. Assessment: policy correctly rejects guessed active states but “verified intent” and independent adjudication are underspecified; hashes cannot recover missing content, and tamper/rollback of intent matters. Failure: counter advances with no slot or write/lock failure; permanently closed/manual recovery may be unavoidable, which is an availability limitation rather than proven confidentiality breach. Locked slot/head missing: recover restrictive state only if exact trustworthy complete contents exist and recovery is authorized; otherwise closed. Correction: R3 and immutable eligibility checks, disposition and escalation, no blind increment. Evidence: fault injection only in later qualification. Blocks preflight: R4.

### 8. Encryption/key boundary — EVIDENCE_BLOCKED_PENDING_INTEGRATED_TARGET_QUALIFICATION
Invariant: authenticated ciphertext, key/nonce uniqueness, no unauthorized key release; wrapping does not establish currentness. Mechanism: CNG AES-256-GCM, one fresh key per encryption, 96-bit nonce, bound AAD and user-scope DPAPI. [CNG](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/ns-bcrypt-bcrypt_authenticated_cipher_mode_info) supports authenticated mode inputs; [Microsoft guidance](https://learn.microsoft.com/en-us/security/engineering/Cryptographic-Recommendations) requires GCM nonce discipline. [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) normally ties protection to user and machine, with roaming exceptions; it is not TPM anti-rollback and an administrator or matching token may defeat isolation outside stated assumptions. An administrative password reset can make data unavailable, subject to recovery options ([Microsoft example](https://learn.microsoft.com/en-us/windows/win32/SecCrypto/example-c-program-using-cryptprotectdata)). Failure: retry reuses persisted key/nonce, or copied wrapper is usable by the same profile absent fresh authority. Specify tag length, CSPRNG failure, backup recovery custody, account/profile changes, dumps/pagefile/temp and copy tracking before implementation. Evidence: wrong principal/profile, tamper, retries and recovery tests. Blocks preflight: not an inherent block to a separately specified disposable DPAPI check; R4 still applies.

### 9. Trusted time — DESIGN_CORRECTION_REQUIRED
Invariant: a deadline-bound grant is denied whenever latest plausible time may have crossed the deadline; ordering is separate from wall time. Mechanism: external NTS time gateway with challenge-bound local interval/uncertainty attestation. Assessment: NTS authenticates NTP messages, not server accuracy or a custom gateway-to-broker attestation; [RFC 8915 §8.6–8.7](https://www.rfc-editor.org/rfc/rfc8915.html#section-8.6) describes delay attacks and downgrade risk. Define trust roots and certificate bootstrap without relying circularly on untrusted time, gateway key/protocol, one-use challenge, interval mathematics including asymmetric delay/source error/drift, monotonic clock scope and suspend/reboot invalidation, expiry and offline denial. A compromised gateway can lie within the declared trust model. For invented-data capability preflight, external time is not needed if it makes no deadline-validity claim and all time-bound access remains denied; this does not remove the requirement for real deadline-dependent operation. Failure: replay/delay or clock rollback makes an expired grant appear valid. Evidence: later authenticated source and failure-mode tests. Blocks preflight: deadline testing yes; a separately specified time-independent read-only preflight need not connect externally.

### 10. Restore/reinstall — DESIGN_CORRECTION_REQUIRED
Invariant: data, keys and restored metadata alone cannot confer current authority. Mechanism: closed scratch and live current witness/inventory checks. Assessment: conditional on R1–R3 and reliable TPM enrollment identity; reinstall/account/OS/TPM changes must fail closed, not create authority. Failure: old backup after withdrawal plus rollbackable anchor or restored receipt state reopens active material. Payload-only, inventory-only, copied key, mixed generations, missing TPM/profile all deny; inventory-only cannot make absent payload available. Correction: bind enrollment identity and recovery authorization; independently establish channel completeness and nonrollback. Evidence: later synthetic mixed-generation, reset/replacement and replay tests. Blocks preflight: R4.

### 11. Capability-preflight safety — DESIGN_CORRECTION_REQUIRED

Classifications below are conditional and do not authorize execution. Exact versions, commands/APIs, identities, paths, effects, evidence and cleanup need separate review and authorization. Failure: a so-called capability probe allocates NV or an unsafe cleanup follows a reparse point. Evidence: approved operation list and observed results in a later preflight. Blocks proposed preflight: yes.

## Adversarial schedule and recovery dispositions

All outcomes below are *requirements*, not observed results. CLOSED means no unwrap, processing or publication until independently justified; if trustworthy evidence is missing, closure may be permanent.

| Scenario | Required disposition / unresolved concern |
|---|---|
| Two concurrent issuers; second broker; copied executable or same-token process | R1 requires non-cooperative issuer exclusion or durable serialization; mutex alone insufficient. Conflicting or unknown state CLOSED. |
| Crash after counter increment, witness absent; witness write fails | CLOSED; never blindly increment or fabricate active state; verified restrictive recovery only after a fully specified one-time binding proof. Possible permanent unavailability. |
| Witness written but lock fails or process crashes before lock | Unlocked witness is not committed; CLOSED. The writable interval is an R1 split-brain risk. |
| Witness locked, head/inventory absent | CLOSED; digest alone cannot reconstruct; only exact authenticated restrictive state under reviewed rules may be installed, otherwise manual adjudication. |
| Slot occupied, counter unexpectedly advances, counter/witness disagree, or capacity exhausted | CLOSED; no choosing another slot or deleting previous evidence. Exhaustion may permanently stop progress; budget and retirement required. |
| Old backup or old inventory restored | Deny unless independently authenticated live anchor and inventory exactly agree; R1/R2 are prerequisites. |
| Active payload restored after withdrawal; inventory without payload; payload without inventory | Withdrawn current state wins; missing material is unavailable; unknown or mismatched state denies. |
| Copied wrapped key appears | Quarantine and account for copy; key possession never authorizes unwrap. Same-profile ability to unwrap makes broker enforcement essential. |
| Service profile/account changed or DPAPI unwrap unavailable | CLOSED; controlled identity and recovery review; do not equate password reset with recoverable data. |
| TPM reset, clear or replacement; app or OS reinstall | CLOSED, detect enrollment discontinuity; no inferred authority, replacement or new anchor without separately approved process. |
| Trusted time unavailable/uncertain, clock rollback, NTS delayed/replayed | Deny deadline-bound use; verify fresh challenge and conservative uncertainty, reject invalid clock epoch and downgrade. |
| Withdrawal races decrypt/output or backup | Receipt fence must order all publication/backup outputs; already escaped data accounted. If drain or receipt recovery cannot be proved, CLOSED. |
| Interrupted deletion | Remain restricted, track every copy/descendant as pending or unverified; no physical erasure claim, no restoration of old access. |
| Lost acknowledgement, repeat operation ID | Reconcile exact witnessed operation and audit, return consistent disposition; never blindly re-advance. A rollbackable deduplication file alone is insufficient. |
