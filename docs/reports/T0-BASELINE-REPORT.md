## 4. Data models, persistence and authentication

- **Plan model:** `PlanRequest`, `PlanSnapshot`, `PlannedSession`, `WorkoutLog`, `SetRecord`, `ExercisePrescription`, `SessionSuggestion`, and `ExerciseSwap` are JSON-encoded in [EngineContracts.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/EngineContracts.kt). A workout log is per session, not a sensor activity.
- **Activity model:** [ActivityRecord.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityRecord.kt) stores `id`, title, type, source, start time, distance, elapsed/moving time, recorded pace, average/maximum HR and elevation gain. [ActivityDetail.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityDetail.kt) stores samples/laps, including optional GPS coordinates. No device field or cadence field is present.
- **Wellness model:** [WellnessRecord.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WellnessRecord.kt) stores id, metric type, value, unit, recorded time and source.
- **Draft model:** [WorkoutEntryDraft.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutEntryDraft.kt) stores unconfirmed editable strings, account/plan/session IDs, log revision and edit timestamp. It is not a `WorkoutLog`.
- **Local database:** [TrainingStore.java](../../android-app/android/app/src/main/java/io/stridelab/privatealpha/TrainingStore.java) uses `stridelab-athlete-v1.db`, SQLiteOpenHelper version 1, and tables `records`, `outbox`, `conflicts`, `cursors`, and `resolutions`. `records` is keyed by `(account, kind, record_id)`. `onUpgrade` throws rather than deleting or silently migrating data. No schema migration files are present in the repository.
- **Local plan sync status:** local writes and generic outbox records are transactional per record. The store exposes `ready`, `acknowledge`, retry and conflict APIs, but no caller of those replay APIs was found in the native app; the UI states plans are device-local and not cloud-synced. Do not interpret an outbox row as a successful external sync.
- **Account separation:** `TrainingRepository` scopes record lookups by account; JSON decoders validate `user_id`; sign-in verifies the session before activating the account. The SQL primary key includes the account. See [TrainingRepository.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingRepository.kt), [ActivityRecord.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityRecord.kt) and [TrainingStore.java](../../android-app/android/app/src/main/java/io/stridelab/privatealpha/TrainingStore.java).
- **Encrypted session storage:** [SessionVault.java](../../android-app/android/app/src/main/java/io/stridelab/privatealpha/SessionVault.java) uses Android Keystore AES-256-GCM and app-private `AtomicFile` storage per account. `TrainingRepository.session` renews near-expiry tokens and retries one request after an HTTP 401; [SupabaseGateway.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/SupabaseGateway.kt) performs sign-in, refresh and user verification.
- **Offline reopening:** cached activities, details, wellness, plans and drafts are loaded from SQLite. The repository tests cover offline reopen and account switching; offline availability does not imply cloud-synced plans or a live provider connection.

## 6. End-to-end manual running-activity linking

1. **Entry point and selection:** A cached run’s Activity Detail shows `ActivityPlanLink`. The unlinked state opens a choice list of approved/paused, manageable plans and run sessions that are not missed/skipped and not already linked. Choices are sorted by calendar distance from the source run; there is no same-date-only filter. See [NativeMainActivity.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/NativeMainActivity.kt) and [ActivityPlanLink.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityPlanLink.kt).
2. **Validation:** `TrainingRepository.linkActivity` requires the activity to be cached and a run, then checks the loaded plan/session state for an existing association. It does not copy source metrics into `WorkoutLog`. The UI says the association does not establish interval compliance.
3. **Persistence and completion:** `PlanOperations.linkActivity` stores the activity ID and prior status in the session snapshot and changes the session to completed. It does not create a native set log. The `Engine1RepositoryTest.manualSourceRunLinksAreUniqueAndReversibleWithoutLosingOfflineRecords` test confirms this behavior.
4. **Unlink:** The linked state exposes an “Unlink recorded run” action. Clearing the link restores `linkPreviousStatus`; the source activity and any separate manual log remain. The test reopens offline, unlinks and verifies the activity remains cached.
5. **Uniqueness:** In a normal single-repository app flow, a second session cannot link the same cached activity; tests verify rejection. `PlanBackup.additions` also rejects duplicated linked IDs across the restored/existing set. There is nevertheless no normalized link table, database unique key, or multi-record transaction, so “transactionally enforced” is **No**.
6. **Offline:** Linking/unlinking is local and can operate offline if the source activity and plan are already cached. It is not a network match and no plan mutation sync consumer is present.

## 7. Twelve verification answers

1. **What causes a strength/calisthenics workout to become Completed?** The explicit “Save completed workout” action passes `complete=true` through `PlanActions.record` → `TrainingRepository.recordWorkout` → `PlanOperations.record`, which stores the log and status. A running session can also become completed through explicit manual linking. The current record validator does not require any set values, which is P0-1. Evidence: [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt), [TrainingRepository.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingRepository.kt), [PlanOperations.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/PlanOperations.kt).
2. **Can time passing or missing imported data automatically modify workout status?** No such transition was found. Missed/skipped requires an explicit UI action and reason; provider absence is not a completion/missed rule. Evidence: [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt), [PlanOperations.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/PlanOperations.kt).
3. **What exactly survives process death, including workout drafts and rest timers?** Successfully written plan snapshots, actual logs and draft rows survive repository restart and are reloaded from SQLite; offline-reopen tests cover repository persistence. Editable input not yet staged successfully is not durable. Rest/hold countdown state is Compose `rememberSaveable`, stopped on `ON_STOP`, and not stored in SQLite; no live timer process-death test establishes guaranteed recovery. Evidence: [TrainingRepository.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingRepository.kt), [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt), [WorkoutPlayer.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutPlayer.kt), [Engine1RepositoryTest.kt](../../native-android/app/src/androidTest/java/io/stridelab/privatealpha/Engine1RepositoryTest.kt).
4. **Is planned-workout-to-activity linking unique and transactionally enforced?** Unique in the normal repository flow and backup restore checks; **not transactionally enforced at the database/storage level**. There is no unique link constraint. Evidence: [TrainingRepository.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingRepository.kt), [PlanBackup.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/PlanBackup.kt), [TrainingStore.java](../../android-app/android/app/src/main/java/io/stridelab/privatealpha/TrainingStore.java), and the link repository test.
5. **How are manually logged runs represented alongside imported runs?** A manually logged planned run is a completed `PlannedSession` with a `WorkoutLog`, displayed separately as a workout log and included in dashboard summaries when dated; it is not an `ActivityRecord`. Imported runs are `ActivityRecord`s with source fields and source metrics. The UI can link a source run to a planned run without merging the records. Evidence: [EngineContracts.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/EngineContracts.kt), [NativeMainActivity.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/NativeMainActivity.kt), [DashboardSummary.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/DashboardSummary.kt).
6. **Which activity provenance and device/provider fields are genuinely stored?** Activity summaries store source string, activity type, IDs, title and listed metrics; no device make/model, watch identity, FIT/GPX file metadata, or cadence is present in `ActivityRecord`. Detail samples/laps carry source activity IDs and recorded metrics. Wellness stores source and recorded timestamp. Evidence: [ActivityRecord.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityRecord.kt), [ActivityDetail.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityDetail.kt), [WellnessRecord.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WellnessRecord.kt).
7. **Can two guided sessions be in progress simultaneously?** There is no global active-session lock. Session status/logs are independent, and each workout route saves its own UI state. Multiple sessions can therefore remain `in_progress`; this is consistent with independent session histories. Evidence: [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt), [EngineContracts.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/EngineContracts.kt).
8. **Can same-date unlinked running activities be queried efficiently?** No dedicated same-date/unlinked query is present. `SupabaseGateway.activities` pages the account’s activity history, local cache loading reads the activity records, and the UI links one activity at a time. The local records key has no `started_at` index. Evidence: [SupabaseGateway.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/SupabaseGateway.kt), [TrainingRepository.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingRepository.kt), [TrainingStore.java](../../android-app/android/app/src/main/java/io/stridelab/privatealpha/TrainingStore.java).
9. **How are Intervals.icu authorization failures distinguished from connectivity errors?** StrideLab HTTP 401/session failures become `ServiceFailure` messages and are retried once after token renewal; transport `IOException`s receive a generic connection/storage message. The connection status model can say connected/disconnected/error/syncing. A provider sync response with `ok=false` or an `error` field is converted to `IOException`, so provider authorization/configuration failures are not consistently distinguished from connectivity failures. Evidence: [SupabaseGateway.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/SupabaseGateway.kt), `TrainingRepository.syncIntervals`, and [IntervalConnection.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/IntervalConnection.kt).
10. **Is there a configurable calendar week start day?** No. Week calculations use Monday (`DayOfWeek.MONDAY`) and calendar headers enumerate Monday through Sunday. No user preference for week start was found. Evidence: `HomePlanHero` in [TrainingScreens.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingScreens.kt) and `TrainingCalendar` in the same file.
11. **Does any in-app running recorder or running guided player exist?** No live run recorder, GPS capture, or running-specific player was found. The guided player appears only when the workout has exercises. Running supports a planned prescription, manual actual-value logging, and linking an already-recorded cached run. Evidence: [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt), [WorkoutPlayer.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutPlayer.kt), [ActivityPlanLink.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityPlanLink.kt).
12. **Where are current status, action, saved/draft, syncing and Missed/Skipped strings defined?** Status values are persisted as string fields in `PlannedSession`; the visible copy is hard-coded in Compose rather than centralized native string resources. Relevant surfaces: [TrainingScreens.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/TrainingScreens.kt) (`PlannedWorkoutCard`, calendar and plan actions); [WorkoutScreen.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutScreen.kt) (save progress/completion, Missed/Skipped, draft copy); [WorkoutPlayer.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/WorkoutPlayer.kt) (set saved, rest, review); [NativeMainActivity.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/NativeMainActivity.kt) (offline, refresh and syncing status); [ActivityPlanLink.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/ActivityPlanLink.kt) (link/unlink); and [IntervalConnection.kt](../../native-android/app/src/main/java/io/stridelab/privatealpha/IntervalConnection.kt) (provider state values).

## 10. Risks, unknowns and recommended next actions

1. Address P0-1’s completion semantics before relying on “Completed” as proof that any actual strength/calisthenics set was saved.
2. Add a transactional association invariant before expanding running-linking to server sync or multiple writers (P0-3).
3. Remove or clarify the generic “start” wording for running cards until an in-app run recorder exists (P0-5).
4. Treat the current Activity Detail as a recorded-stream summary, not the requested Strava-like map/panel/tab experience. Garmin route/metric support requires new provider ingestion and richer provenance, not just a source label.
5. Plan migrations deliberately: `TrainingStore` is schema v1 and currently rejects upgrades rather than migrating. Keep the existing legacy app/WebView data path separate.
6. Keep local-only plans/drafts distinct from actual upstream sync; the local outbox API is not evidence that plan mutations are replayed.
7. Permanent private signing and device-update compatibility remain a separate pre-phone-installation gate. Do not use the ephemeral CI debug signer for an update.
8. This report closes T0 only. Review the report and preserve the verified checkpoint; do not treat this audit as authorization to begin Garmin, UI reconstruction, Engine 2.0, or T5A implementation.
